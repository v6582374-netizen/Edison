# Gemini 3.8 Flash 容量与长播客成稿研究

研究日期：2026-10-26。对应决策票：[模型容量与真实长播客：是否还需要固定分段成稿](https://github.com/v6582374-netizen/Edison/issues/64)。本文件是研究资产，不是本地 tracker。只读研究；没有调用模型、重跑任务或改变生产配置。

## 结论

Gemini 3.8 Flash 的官方输入上限为 1,048,576 tokens，单次输出上限为 65,536 tokens。正常 2–4 小时播客的纯文字译文通常可以完整作为输入；这不证明全部译文能在单次输出中完整重生成。固定约 1,000 token 小块已经不能单凭输入窗口不足获得合理性，但是否采用全文一次输出，仍须经过实际文本计数、接入链路有效限制核验和质量对照。

当前接入还有一个关键差异：Edison 请求 8,192 输出 tokens，代理先转换该字段，随后在 Antigravity 的非 Claude 路径删除它。因此“模型支持 64K”和“应用申请 8K”都不能直接表述为当前上游有效输出限制。

## 官方事实与来源

- [Google 精确型号页](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash)（页面更新 2026-10-22）：模型代码 `gemini-3.8-flash`，Stable；输入 1,048,576，输出 65,536 tokens。
- [Google Cloud 精确型号页](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-8-flash)（页面更新 2026-10-22）：同样的限制，GA，支持 Count Tokens API。这是官方渠道能力，不能证明第三方代理完整暴露它。
- [Google token 说明](https://ai.google.dev/gemini-api/docs/tokens)：英语 100 tokens 大约对应 60–80 词；`count_tokens` 可在请求前计数，响应 usage 用于观察实际消耗。Gemini 3 使用独立的 1M 输入与 64K 输出预算。
- [Google 长上下文说明](https://ai.google.dev/gemini-api/docs/long-context)：上下文可用于提供完整相关资料；Gemini 3 与 Gemini 4 的输入输出预算规则不同。动态 `/latest-model` 页面已转向 Gemini 4 Argon，不能作为 3.8 的固定规格来源。

## 2–4 小时：估算与实测必须分开

估算假设为英语每分钟 120–180 词，不代表对本项目样本的语速测量。2 小时约 14,400–21,600 词；4 小时约 28,800–43,200 词。使用官方英语换算，范围约为 18K–72K tokens。中文译文不能套用英语词数换算。若仅作保守情景，将中文 token 规模暂设为英文的 3 倍，再同时提供原文和译文，输入约 72K–288K tokens，仍低于 1M。这个 3 倍系数不是已验证转换率，不能替代中文实际计数。

只读检查了之前调查留下的三份完整翻译阶段检查点。修订译文累计约 6,031–23,655 Unicode 字符、16,195–68,095 UTF-8 字节，修订块数量为 4–16。检查点中的 `source` 是 64 字符标识，不能当作原文。原始材料保留在服务器私有目录；这里只发表聚合范围，不发表内容、视频标识或标题。

这些样本未核实时长，也未使用 Gemini tokenizer 计数，不能称为 2–4 小时样本实测，更不能以 UTF-8 字节等同 tokens。尚无足够证据证明项目最长播客的中文整篇输出低于 64K。

## 当前应用和代理的限制

Edison 来源基线为 `390a22d`：

- `src/youtube_strataread/workbench/translation.py:235` 固定 `output_limit = 8192`，随后传入 `max_tokens`，也用于本地预算预留。
- 同文件约 392 行之后的成稿阶段复用上游分割器，以约 1,000 token 的块整理译文。该分割器用 `gpt-4` tokenizer，并非 Gemini 精确计数器。

2026-10-26 通过 SSH 只读检查已部署代理版本目录 `aiclient-4c4c7749` 的公开源码（未读取认证正文）：

- `src/converters/strategies/OpenAIConverter.js:1375–1378` 将 `max_tokens` 转换为 `generationConfig.maxOutputTokens`。
- `src/providers/gemini/antigravity-core.js:71` 将 `gemini-3.8-flash` 映射为 `gemini-3.8-flash-low`。
- 同文件约 174 行的本地元数据写 65,535，和官方 65,536 相差 1；它是代理元数据，不是独立证明的服务端限制。
- 同文件 `607–615` 先按元数据裁剪，再对非 Claude 路径删除 `generationConfig.maxOutputTokens`。因此不能说 8,192 已作为硬上限传到 Google。

未发请求，未验证服务端默认输出长度、实际长输入接收上限、截断行为、长请求超时或当前代理 count-tokens 支持情况。以上是源码路径证据，不是网络报文实测。

## 候选方案的边界

| 方案 | 优点 | 边界与待验证问题 |
| --- | --- | --- |
| 固定小块 | 单次失败损失小、恢复粒度细 | 破坏句子/数字边界；调用多；标题与术语易不一致；不能因旧习惯保留 |
| 自然章节分别处理 | 语义更完整，仍可独立恢复 | 章节长度不均，需要输出预算上限及长章处理 |
| 全文输入，按章节输出 | 每次可利用全局术语、论证顺序，输出有界 | 重复输入成本和延迟；缓存可用性未知；必须防重复与漏章 |
| 全文一次输出 | 最少编排与拼接，整体编辑空间大 | 输出容量、忠实度、耗时、失败重做成本；适用长度不能只看输入上限 |

全文理解与分段输出并不互斥。保留完整内容的目标下，可以先评估可追溯自然章节，再决定哪些短文一次生成、哪些长文采用全文上下文配合章节输出；这里不替用户锁定架构。

## 下一步验证方法

1. 用获准既有 2–4 小时材料，只统计时长、原文/译文字符及对应 Gemini token 数，包含系统提示和术语表；确认代理是否支持无生成计数或可靠本地 tokenizer。
2. 在隔离测试中验证实际请求参数、默认及显式输出行为、usage、结束原因、长请求超时；不得直接把官方 API 参数语义套给 Antigravity 接入。
3. 对同样资料比较上述方案，记录内容覆盖、事实与数字语义一致性、术语一致、可读性、真实 token 成本、耗时与失败重做量；先有基线再决定是否保留三阶段翻译。
4. 可恢复进度、预算和诊断证据需要独立于分块大小设计。研究不授权重新生成现有失败任务或改变验收观察周期。
